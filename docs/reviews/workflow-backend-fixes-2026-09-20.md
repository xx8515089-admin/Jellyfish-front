## BE-01：为未覆盖入口提供可靠的提交恢复契约

### 现有请求证据

以下路径前缀为 `/api/v1/studio/`，列出的参数是本次审查关注的现有前端请求，不是建议新增字段的最终规范。

| 接口 | 前端当前提交方式 | 前端证据 |
| --- | --- | --- |
| `storyboards/dubbing/generate` | lineId、outputFormat、可选 modelId | `src/services/studioDubbing.ts:51` |
| `storyboards/imagetovideo/generate` | imageGenerationId、prompt、模型/尺寸/时长、scope/panelRevision 等；无 clientRequestId | `src/services/generated/models/ImageToVideoGenerate.ts`；`ImageToVideoModal.tsx:174` |
| `assets/generate` | assetId/造型、提示词、风格、模型、尺寸等；返回后才能拿 taskId | `src/services/studioAssetGeneration.ts:656`、`:2815`；`ProjectAssetsStep.tsx:3341` |
| `scripts/imports/chapters/create` | scriptImportId、rawText | `src/services/studioScripts.ts:375`；`ProjectCreatePage.tsx:2526` |
| `scripts/imports/assets/extract` | scriptImportId | `src/services/studioScripts.ts:417`；`ProjectCreatePage.tsx:2622` |

组件路径位于 `src/pages/aiStudio/project/`。普通 images/videos 已有 clientRequestId + submission 查询；批量视频也有独立冻结请求与查询流程，不应视为完全缺失。

### 要解决的场景

服务端已受理，响应在客户端收到前丢失。前端没有 taskId，无法判定该重试原操作还是创建新任务。仅限制按钮、禁止弹窗关闭，不能消除刷新、多标签页及网络层重试带来的不确定性。

本地已复现配音超时后前端再次 POST；是否会真的创建第二任务/计费，必须查服务端实现。

### 先核实

1. 各入口是否已有 clientRequestId/header、业务请求号或 run/revision 幂等能力？作用域、有效期、冲突返回是什么？
2. 未获得任务 ID 时，能否按原提交身份查询权威受理结果？仅“最新任务”列表不能证明是哪一次请求。
3. 请求正在提交、查不到结果、服务端无法确认 provider 是否受理时，分别返回什么？
4. 资产提取是每个 import 只能执行一次，还是允许随章节版本重新提取？不能用永久 importId 去重阻止合法新版本。
5. 新增相同文本的分集是否允许用户主动再次添加？重试身份不能只用 rawText/hash，否则会吞掉合法新操作。

### 若能力不足，补齐要求

- 接受稳定客户端请求身份，并将“请求身份、请求参数快照/摘要、当前受理状态、任务或结果 ID”持久化。
- 同账号/租户 + 操作类型 + 请求身份唯一；同身份同参数返回同结果，参数不一致明确冲突，不启动新作业。
- 查询/重放始终校验所属账号与对象权限；记录的保留期应覆盖实际任务时间与恢复窗口，并在契约中明确。
- 业务受理落库和作业派发需要可恢复的一致性机制。并发、进程重启、供应商超时后不可凭未知状态重新创建一份逻辑任务。
- 若调用供应商也有不确定窗口，利用供应商请求身份/查询或人工核查状态解决；不要宣称仅靠前端 UUID 就能保证供应商严格执行一次。
- 计费、额度预留、成功结算、失败退款必须绑定同一逻辑任务身份，避免重复回调/重试重复记账。
- 新增分集需返回同一次操作创建的稳定 ID 集合；提取资产需绑定输入章节版本/修订号，允许用户明确发起新版本操作。
- 独立图生视频与配音可复用内部能力，但外部路由/类型需要明确支持，不能让前端猜测普通媒体 submission 接口也能查询它们。

### 验收用例

| 场景 | 期望 |
| --- | --- |
| 同请求身份并发发送 10 次 | 返回同一逻辑任务/分集集合；只有一份受理结果 |
| 同身份但更换提示词、模型或输入版本 | 明确冲突；原任务不变，不新增计费 |
| 入库后丢响应，再查询和重放 | 找回原受理结果，不生成新结果 |
| 派发前/后进程重启 | 状态可恢复，不靠重新点击创建另一任务 |
| provider 超时、重复回调 | 保持待核查或确定状态；计费幂等 |
| 查询暂未可见 | 明确短暂未知/处理中语义；客户端不被诱导改用新身份 |
| 正常主动再生成/新章节版本提取 | 使用新身份，合法创建新任务 |

## BE-02：明确错误响应中的受理语义

### 证据与边界

`src/pages/aiStudio/project/workflowMediaPolicy.ts:29` 当前会把 HTTP 502 + body.code=502、没有 errorCode 的错误当作明确拒绝。`REPRO FE-04` 确认这会使前端丢弃原身份。

HTTP 502/网关超时本身不能证明业务未受理。这里尚未证明线上 Java 后端会返回该具体 envelope，需后端提供实际网关和业务错误样例。

### 必须明确的语义

| 受理情况 | 客户端应采取的动作 | 服务端契约要求 |
| --- | --- | --- |
| 明确未受理、没有创建作业/预留未保留 | 修正参数后允许新提交 | 有明确错误码及可依赖的“不产生作业”保证 |
| 已受理 | 跟踪原任务 | 返回或能查询稳定任务 ID |
| 受理结果未知 | 保留原身份，查询/原样重放 | 不伪装成普通可重新生成的校验失败 |
| 相同身份参数冲突 | 保留原请求，提示冲突 | 返回原身份冲突，不能派发第二次 |
| 已受理任务最终失败 | 按用户意图新建重试或使用显式重试接口 | 与“提交时未受理”区分，退款/计费状态可核实 |

可使用现有结构化 `errorCode`；如需增加 acceptance 字段，其枚举和含义由双方确定。上述表是要求，不是宣称已有某些字段。

### 交付与验收

- 提供普通媒体、批量视频、资产、配音、独立图生视频的错误码清单，逐项标记是否保证未受理。
- 提供校验拒绝、并发冲突、额度不足、供应商超时、数据库/队列异常、网关 502/503 的样例。
- 测试“任务已落库后抛异常”的场景；前端仍能以原请求身份查回，不能错误释放身份再创建。
- 前端使用正向白名单；未知新错误码自动保守保留身份。现有业务 `code=502` 不能作为未受理的唯一依据。

## BE-03：统一终态、轮询和产物就绪矩阵

### 现有契约

`docs/contracts/workflow.openapi.json:630` 以及 `src/services/generated/models/WorkflowMedia.ts:18` 已有 `terminal`、`shouldPoll`、`pollAfterSeconds`、`outputReady`。普通前端 hook 尚未正确使用，属于 FE-05；不要求后端重复新增同名字段。

### 待核实/修正

- status=3 表示供应商完成还是产物已经可访问？搬运/转码阶段能否带 fileId/url 但 outputReady=false？
- 最终失败、人工核查状态各是什么 status，terminal/shouldPoll 应如何组合？是否允许 status=2 而 terminal=true？若不允许，应有服务端约束和测试。
- outputReady 的判定是数据库有 URL，还是可供展示/导出的文件已经就绪？缩略图未就绪应与主产物分开定义。
- activeTasks 是否包含“生成结束但产物未就绪、仍需轮询”的记录？刷新后不能漏掉该阶段任务。
- detail、activeTasks、historyPage 是否保持相同 generation 身份和状态含义？历史暂时滞后时如何收敛？
- `pollAfterSeconds` 缺失、为零及异常值的含义；前端是否应使用默认间隔。

建议给出完整状态矩阵和样例响应，明确合法/非法组合。产物准备中不要给出可直接导出的承诺；人工核查状态不要要求前端无限自动轮询。

### 验收

模拟排队 → 运行 → 供应商完成/产物准备 → 可用，以及失败、待核查路线；每个阶段刷新页面后均可继续跟踪。以相同样例同时验证后端返回、前端停止轮询判断、历史显示和导出可用性。

本次注入的两个异常组合已复现客户端错误处理；其线上出现频率尚未验证，不应据此推断服务端已产生错误状态。

## BE-04：核实配音生成是否冻结用户提交的完整输入

### 证据

`StoryboardDubbingPanel.tsx:565` 顺序调用 updateLine → updateSettings → generate。`studioDubbing.ts:51` 的 generate 仅传 lineId、输出格式、模型；现有前端类型没有 expectedRevision 或输入快照字段。

### 风险与核实条件

两个标签页/协作者在三个请求之间修改台词、角色音色或 run 设置时，generate 可能读取到与用户刚确认不同的值。该风险取决于服务端是否已有快照、锁或版本校验；未在本次确认实际发生。

后端应说明生成任务读取的是哪个版本，以及任务是否在受理时冻结台词、角色/音色、音量、语速、情绪、模型、格式和对应输入版本。若已保证，提供契约供前端接入；若不能保证，则补以下一种方案：

- generate 接受完整输入快照，受理时原子校验并保存；或
- 更新返回 revision，generate 校验 expectedRevision（含所引用音色/设置版本），不匹配时明确拒绝受理。

任务执行和历史显示都使用受理时快照，不能在排队执行时重新读取可变的最新台词。验收：受理后修改台词不改变已排队作业；受理前版本变化明确冲突，避免生成错误内容后才发现。

## 导出链路的额外核实项（不计入已确认后端缺陷）

`src/services/storyboardExport.ts:35` 的 `freezeExportRequest` 只冻结图片/视频 generationId；音频导出不发送音频版本身份。若 preview 与 zip 之间同一句配音产生新成功版本，两次接口是否使用同一个输入快照需要确认。

若产品承诺“下载与预检严格相同”，后端应支持预检快照 token 或显式音频版本集合，并校验权限/有效期；前端配套透传。若现有设计就是 zip 时取最新，应明确并展示该语义，不将其误报成已确认缺陷。验证方式是在 preview 后、zip 前完成一条新配音，再比对清单与 ZIP。
