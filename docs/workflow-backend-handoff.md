# 项目创建第一至第四步：后端对接与待确认事项

日期：2026-09-14  
范围：基本信息 → 剧本分集 → 资产确认 → 片段编辑  
性质：待确认契约与实施建议，不是已经上线的 API 规范。

## 1. 本次审查边界

本文件依据当前前端实现整理。未对实际部署的后端执行接口联调，不能据此前端代码认定某个后端能力不存在。

- “已观察”指前端可直接确认的行为。
- “待确认”指后端应提供现有接口契约；已有能力可直接复用，无需重复建设。
- “建议变更”中的字段和响应示例是建议方案，不代表现有接口已经支持。
- 当前前端 TypeScript 检查、111 项资产相关测试通过，但未覆盖真实并发写入、跨片段生成和付费任务联调。

目标：优先防止内容覆盖、ID 错配和任务状态丢失，再完善历史查询与媒体加载性能。

## 2. P1：分集更新接口与并发保护

### 已观察

第二步使用以下接口读取、创建分集：

- `GET /api/v1/studio/scripts/imports/chapters/list?scriptImportId=...`
- `POST /api/v1/studio/scripts/imports/chapters/create`

但编辑分集使用 generated client 的：

```http
PATCH /api/v1/studio/chapters/{chapter_id}
Content-Type: application/json

{"title":"第一集","raw_text":"分集正文"}
```

标题和正文失焦均可触发保存，同一分集目前可能有多个写请求同时进行。前端对响应的检查只能避免覆盖当前输入，不能阻止旧请求覆盖数据库中的新内容。

### 后端需要确认或补充

1. 上述列表中的 `id` 是否就是 PATCH 使用的 `chapter_id`，是否对应同一张业务实体表。
2. 当前部署是否实际提供该 PATCH 路由；若应使用其他接口，请提供准确路径、方法和 OpenAPI DTO。
3. 正文字段究竟是 `raw_text` 还是 `rawText`，返回字段及长度限制是什么。
4. 是否已有修订号或 ETag 并发保护；若无，建议增加数据库级乐观锁。
5. 更新成功后如何使资产提取、分镜等下游结果失效；不可编辑的分集是否由后端拒绝修改。

### 建议的并发契约

沿用确认后的现有路由，不强制新增路由。以下字段仅作方案示例：

```json
{
  "title": "第一集",
  "rawText": "最新正文",
  "expectedRevisionNo": 7
}
```

成功返回持久化后的分集及新修订号。修订冲突返回可识别的错误码，例如 `REVISION_CONFLICT`；实际 HTTP 状态与错误信封沿用项目约定并写入 OpenAPI。不能静默覆盖，也不能由前端自动更换版本号重试。

前端同时需要按分集串行保存，并在进入资产提取前确认相关修改已保存；后端乐观锁用于保护跨窗口、跨设备写入。

### 验收

- A、B 两个窗口读取同一修订，A 保存成功，B 保存收到冲突，A 内容保持不变。
- 连续修改标题和正文，刷新后内容与最后一次确认保存一致。
- 列表返回的 ID 能直接用于更新和重读，未发生实体错配。
- 拒绝越权和不可编辑分集的修改。

## 3. P1：图片与视频生成任务的查询和恢复契约

### 已观察

已有前端调用：

- `POST /api/v1/studio/storyboards/images/generate`
- `POST /api/v1/studio/storyboards/videos/generate`
- `GET /api/v1/studio/storyboards/videos/detail?id=...`
- `GET /api/v1/studio/storyboards/media/history?segmentId=...`

导演台生图提交后只显示“任务已提交”，生图响应在前端被声明为 `unknown`。片段页视频状态按片段存储，但共用一个请求和计时器，生成另一个片段时可能停止前一个片段的查询。这一轮询问题由前端修复，不要求后端新建视频生成接口。

### 后端需要确认或补充

1. 生图、生视频的提交响应分别返回哪些 ID：任务 ID、生成记录 ID、图片/视频实体 ID。
2. 图片状态应使用哪个现有接口查询；视频 detail 的 `id` 是哪一种 ID。
3. 提供完整状态枚举及终态定义，明确 `progress=100` 是否代表产物已可读取，不能让前端凭状态名称猜测。
4. 片段重新打开时，从哪里恢复未完成任务。优先复用现有任务列表或片段详情；已有接口则只需补齐文档。
5. 明确失败原因、取消状态、建议查询间隔，以及失败或重试时的积分处理。
6. 确认生成提交是否已有幂等机制；若没有，建议支持客户端请求标识，避免网络重试导致重复任务、重复扣费。

建议提交响应至少提供可查询的稳定标识和片段归属，例如下列语义字段；实际名称以正式 DTO 为准：

```json
{
  "taskId": "task-identifier",
  "generationRecordId": "record-identifier",
  "segmentId": "segment-identifier",
  "status": "queued"
}
```

不要求增加新的任务类型；复用现有任务系统即可。

### 验收

- A、B 两个片段同时生成，均可独立查询到完成或失败。
- 页面刷新、关闭后重开，能恢复未完成任务。
- 生图完成后历史中能查询到结果和输出文件；失败有明确原因。
- 同一幂等标识重复提交不会重复创建或扣费。

## 4. P1：多参生图字段与积分估算

### 已观察

导演台当前生图请求包含：

```text
segmentId, modelId, prompt, aspectRatio, resolution,
quality, visualStyleId, references
```

其中图片 `resolution` 当前为数字，如 `2`；视频分辨率为字符串，如 `720p`。图片参考项包含 `referenceType`、`fileId`、`displayName`、`useOnly`、`doNotUse`。导演台接入文档规定角色图类型为 1、站位图片类型为 5；不能把视频参考类型编号整体搬到图片请求。

片段页目前复用 `POST /api/v1/studio/assets/generate/estimate` 查询图片积分，请求为 `modelId + quality:null + resolution`。主面板生图按钮仍未接入提交，属于前端待办。

### 后端需要确认

- 资产生图估算是否适用于分镜多参生图；参考图数量、画幅或其他参数是否改变价格。
- 若价格不同，提供现有分镜生图估算接口；没有时再补充，不应继续展示不准确的资产价格。
- 图片 `quality`、`visualStyleId` 的省略、`null`、默认值语义，及模型是否要求显式质量档位。
- `references` 的完整 DTO、数量上限、顺序与提示词编号规则，`useOnly/doNotUse` 是否允许当前自由文本。
- 视频估算是否还依赖 `generateAudio`、参考视频时长等字段；若依赖，明确哪些由服务端获取，哪些必须传入。
- 返回模型能力与实际生成校验是否一致。

### 验收

同一模型与参数在估算、提交和最终账单中的口径一致；遇到价格变化、积分不足或不支持的参数时有明确错误。前端显示数字不能作为后端扣费依据。

## 5. P2：统一 ID、风格与来源字段

### ID

当前前端存在将数字字符串 ID 转成 `Number()` 的代码。若后端使用超过 `Number.MAX_SAFE_INTEGER` 的长整型 ID，将产生精度损失。

请确认 ID 范围。对可能超限的 ID，建议 JSON 响应使用字符串，请求支持原字符串；同时在 OpenAPI 中定义清楚。前端需配套移除不安全转换，不能只改后端输出。

需要区分：`scriptImportId`、分集 ID、`segmentId`、`assetId`、`lookId`、`fileId`、任务 ID、生成记录 ID、工程 ID 和各类修订号。工程修订与参考列表修订不能互换。

### 风格

第四步目前按风格名称反查 ID，同名时可能选错。前端应改用 ID 作为选择值；后端确认列表稳定返回 ID，并明确 `null` 的“无风格”语义。不要依赖名称唯一性修补前端映射。

### 来源追溯

历史归一化目前把 `item.id` 当作 `generationRecordId`，随后用于 `directorDesks/generationOrigins`。

请确认历史项的 `id` 是否就是来源查询所需的生成记录 ID。若不是，请明确返回 `generationRecordId`，前端按该字段读取，避免用图片/视频实体 ID 查询来源。

### 验收

- 超安全整数范围的 ID 全链路往返不变。
- 同名风格能够按 ID 正确区分。
- 图片和视频历史均能查询到正确来源工程修订。

## 6. P2：历史查询与缩略图性能

### 已观察

前端现已显示图片和视频混合历史，并每 10 秒补查。无视频封面时，缩略图会加载视频并解码一帧；记录多时请求和解码成本上升。

### 后端建议

1. 为图片、视频产物提供轻量静态 `thumbnailUrl`；视频生成完成时生成封面，图片缩略图不直接返回原始大图。
2. 明确历史默认排序，例如最新记录优先，并保证同时间记录的稳定排序。
3. 历史较多时提供分页或游标，返回稳定的记录键；前端同步接入分页后再启用，避免旧客户端只显示首批记录。
4. 若已有版本号、ETag、更新时间或增量查询能力，请提供用法，减少未变化列表的全量传输。
5. 确认媒体访问支持浏览器缓存、视频 Range 请求和正确的 Content-Type；受保护资源的缓存仍须遵守鉴权策略。
6. 明确历史列表是否包含运行中、失败任务，以及哪些状态拥有可展示的输出文件。

前端配套：按任务状态启停轮询，数据未变化时复用对象，仅加载可见缩略图。服务端封面不会自动解决前端重复渲染问题。

### 验收

- 历史缩略图展示不需要为每条记录读取视频数据。
- 新产物可查询，列表排序稳定，分页无重复遗漏。
- 重复查看同一媒体能有效利用缓存；视频可按需请求数据片段。

## 7. P2：导出剪辑表产品契约

第四步目前只有占位提示。先确定导出内容和格式，再判断是否需要后端：

- 若只是当前列表 CSV，可由前端生成。
- 若需要完整工程数据、素材打包、剪辑软件工程格式或异步导出，则由后端提供对应任务能力。

需确定导出范围、历史版本选择、未完成任务的处理、图片/视频/对白字段以及下载文件有效期。不能在未明确格式前直接新建一个泛化导出接口。

## 8. 纯前端问题，不转成后端需求

| 问题 | 前端处理 |
